## What v1.2 is

A bounded, research-informed execution profile for using the existing LM Studio setup to complete and evaluate one useful local work task. It connects /goal, /journey, a concrete task contract, actual runtime checks and the owner's 30 assurance attributes.

The user-supplied SaaP example governs the sensemaking approach for this task: understand, organise, explore, challenge, make sense, recommend and identify practical action. PaP2 specifies how the chosen action is configured or implemented, checked and handed over. These are complementary responsibilities, not a ranking of prompt categories.

It is not a new operating architecture, a replacement router, a revision of the owner's original sensemaking instruments, or a declaration that a prompt is already an executable pipeline. Its PaP2 instruction form specifies the process; Codex must implement or configure, run and verify the applicable process before claiming pipeline execution.

The initial task is a fictional training enquiry. Workshop planning, general source summaries, additional hosts, additional providers and corporate use are later extensions.

The best-fit reviewing function is a Principal Human-AI Systems Assurance Reviewer, combining evidence scrutiny, architecture, service design, evaluation and workload economics. Role labels do not supply independent review or authority.

### /goal

Enable Will to turn one fictional training enquiry into an accurate, inspectable requirements summary, missing-information list and response draft through his existing local LM Studio setup, with clear evidence of what ran and the effort still required.

Four goal tests:
- Value: does this address a recurring preparation burden?
- Usefulness: is the output actionable and correct for the supplied facts?
- Robustness: do missing evidence, service failure and hostile source text produce honest outcomes?
- Affordance: can Will inspect, correct, cancel and resume the work?

Technical done means one qualified route, a reproducible enquiry example, relevant negative checks, startup/reversal instructions and a truthful evidence record. An existing direct-chat/configuration route can satisfy this without new code.

Target-machine access is required for a target-machine verification claim. If absent, finish the independent project work and supply a minimal read-only evidence-collection script; report PARTIAL with the exact remaining dependency.

Human benefit remains NOT_MEASURED until Will supplies actual review, timing and acceptance observations. Do not claim a percentage improvement from model speed, fictional fixtures or this prompt's existence.

### Sensemaking before the implementation choice

Apply the user's SaaP moves in proportion to the problem. They are reasoning checks, not mandatory headings or a second workflow platform.

| Move | Application to this task |
| --- | --- |
| Understand | Identify the actual decision, desired outcome, beneficiary and current burden before selecting a model or tool. |
| Organise | Separate user-confirmed facts, observed device state, source-reported claims, hypotheses, assumptions and unknowns. |
| Explore | Investigate plausible bottlenecks and alternatives, including an adequate existing/manual process. Consider who gains time and who inherits review work. |
| Challenge | Examine contradictions, missing evidence, competing explanations and the strongest counter-case. Do not infer that token cost caused productivity gains or that a Git optimisation speeds model inference. |
| Make sense | State what the evidence reasonably means, why it matters for this host/workflow, and the principal uncertainty limiting the conclusion. |
| Recommend | Compare proportionate options, costs, disadvantages and implications; explain the smallest justified next increment. |
| Act | Specify the next action, owner, input, output and acceptance check; execute only within the authorised scope and actual host controls. |

If missing information materially changes the next dependent action and cannot be inspected, ask the single most important clarifying question first. Continue independent authorised work. State reversible assumptions explicitly; do not invent facts or ask a routine questionnaire.

For a simple issue, a short decision note is enough. For a contested choice, use: what is happening; what matters; what may be behind it; what may be missing; what it means; options; next action. Omit headings that add no value. End with the recommendation, key uncertainty, falsifier and next step rather than framework completion for its own sake.

Keep the strongest counter-case and one observable falsifier in the decision note. If manual preparation is already faster, or correction cancels the saving, simplify or stop that AI route.

Do not import corporate formation gates, proposed mandatory waiting periods or role councils into this reversible local pilot. Preserve any actually applicable project controls and existing authorisation.

### Versioned working state and efficient reuse

Retain ordinary Git and existing project conventions. Do not build a Git server, install a custom Git distribution or change remote hosting for this pilot.

Bind a run to input, prompt, model/configuration and code revisions. Before applying a prepared change, recheck the expected base revision; if it changed, inspect the difference and repair or rebase within scope. Never overwrite a stale base silently.

When acceptance depends on several artefacts, pin their exact revisions in one manifest and check the complete set. Do not infer a consistent release from independently current branch names or mix evidence from different revisions.

Keep accepted checkpoints and candidate changes distinguishable. Digests support identity and change detection; they do not establish factual truth, human approval, tamper-proof storage or backup.

Do not treat an old cached answer as fresh evidence or cross confidential/client boundaries. Add a cache only if repeated work justifies its complexity.
